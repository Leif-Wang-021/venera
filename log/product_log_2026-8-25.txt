## 一、用户实测复核（08:1x，logs.txt 07:55~08:10 会话）+ settled 态棘轮缺陷修复（08:4x）

### 1. 复核前提确认
- 所读文件为**今天生成**：内容跨度 `2026-08-25 07:55:43→08:10+`，含 0 条 8-24
  时间戳；版本指纹（`probing disabled`/`SETTLED`/封顶冷却）确认为 v4 安装包。

### 2. 复核结论
- **原问题（无限卡死、停顿指数升级）已解决**：121+ 章持续推进、零失败、
  非 200 = 0；
- **未达速度目标并发现新异常**：卡顿(>12s)=20 次，呈锯齿——每 ~9~10 章
  一轮"26s 排空 + 30s 冷却"；且 `safeThreads` 被**永久棘轮下调 2→1**
  （threads=1 下风控照样发生，降档零收益）。

### 3. 新根因（有日志实证）
- 源站限流方式已从"HTTP 210 报文"变为**连接级重置**：触发风控判定的请求
  网络层耗时仅 0.3s 且 200（与 BACKOFF 同秒），时间消耗在 JS 内部
  连接重试（全日仅 6 条 `RhttpIncompleteMessage` 样例，落点与排空窗吻合）；
- 稳态节奏由源 JS 自限流主导：threads=1 下请求起始间隔 3.2~5.0s 而单次
  耗时仅 0.3s——并发已非瓶颈，降并发纯属损失（实证：threads=1 与 2 的
  风控周期完全相同）。

### 4. 全局优化（fetch_concurrency_controller.dart，零下载逻辑改动）
- 新增 `_healthySinceResume` 计数：每次转移清零，成功且非风控的完成 +1；
- NORMAL 态风控分流：
  - 恢复后已有健康成功（>0）→ 判定为长惩罚窗的周期性配额事件，
    **pause-only**：只进 30s 冷却暂停，**不裁撤 worker、不下调 safe**；
  - 恢复后零健康即再风控 → 该级别确实过热，保留原裁撤语义（-1 并夹紧 safe）；
- 日志可观测：BACKOFF 行新增 `, pause-only` 标记。
- 单测扩至 **40 断言全过**（重写 T14 为"周期性风控不裁撤"，新增 T15a~c
  "零健康立即再风控才裁撤"）。

### 5. 回归（08:28，hot_manga 19 章 headless）

## 二、用户目标升级："整体更快 + 卡顿无感知" —— 发起节奏器（09:2x）

### 1. 需求与依据
- 用户明确：宁可节奏平稳也要消除周期性冻结（v5 锯齿：7章/31s 抓取后
  冻结 48s = 22s JS 排空 + 30s 盲冷却）；
- 日志实证：冻结期配额仍在回充——若发起间隔贴合回充速率，
  同等平均速度可**连续流动、零冻结**。

### 2. 实现（全局，控制器 + 派发层各一处）
- `fetch_concurrency_controller.dart`：
  - 新增 `_startGapMs` 学习间隔 + `bookStartSlot()` 时间槽 API；
  - AIMD：每次 BACKOFF 事件 ×1.5（种子 4s、封顶 12s）；
    每 20 个健康完成 −250ms，下限 0（健康源零开销）；
  - 节奏器生效（gap>0 且 probeDisabled）时，settled 态冷却
    30s→10s（排空已在 JS 内完成，盲停冗余）；BACKOFF 行新增 gap 观测；
- `download.dart` worker：派发前预订时间槽并在**不占许可**的情况下等待
  （延迟计时在 stopwatch 之前，不污染风控判定；gap=0 时零开销直通）。

### 3. 验证
- 单测扩至 **52 断言全过**（T16 种子/预订、T17 精确 AIMD 增长模型、
  T18 长健康归零、T19 冷却覆盖 10s）；
- 回归（09:16，hot_manga 19 章）：成功 **19/19**；卡顿(>12s)=**仅 2 次**
  （57.7s 首触一次性 + 25.6s 探测失败一次性），节奏器生效后零新增卡顿；
  吞吐 **11.9 章/分**（v5 为 10.7）——更快且平滑；
- 三版对照（同漫画）：v4 卡顿20/8.1分 → v5 卡顿27/10.7分 →
  v6 **卡顿2/11.9分**。
- 安装包重建 09:20。

### 2. 采用的算法（用户提供 policy.py，全局通用、零源名特判）
信号仅两个可观测代理量：`是否被惩罚` 与 `惩罚代估 pest`；
映射到控制器：
| policy.py | Venera 实现 |
|---|---|
| w=发起间隔总等待 | `_wMs` 绝对地板：下次发起 ≥ 上次实际发起+w（源脚本自节流计入 w） |
| burst_M | `noteStart()` 实测相邻发起间隔 EMA |
| pest=gap−w | pest=风控请求耗时−健康耗时EMA(α0.3) |
| 分类 pest<8s | healthy：×0.55/3ok 快速归零；non：×0.8/6ok |
| w0=clip(M+0.5,1.5,7) | 首次风控种子（默认 M 无数据时 3.5s） |
| max_pun=clamp(Fb/pest,1,3) | 预算耗尽即冻结探索（防反复排空） |
| inc 0.9 / cap 8 | 爬升 +900ms/次，封顶 8000ms |

## 四、下载器两项功能调整：取消即删本地文件夹 + 列表/下载并行（15:2x）

### 1. 取消任务时删除本地文件夹
- 原实现的缺陷：① 仅覆盖部分分支（已入库任务且未选章节时不删任何内容）；
  ② 按章节清理时用原始章节名拼接目录，未走 `getChapterDirectoryName`
  净化名——实际删除不生效；③ 同步分支失败无日志无提示。
- 重写 `cancel()`：先取消全部在途图片包装器并唤醒管线 waiter，
  再异步执行 `_deleteLocalFolderAfterCancel()`：
  - 未入库任务 → 删除整个任务文件夹；已入库任务 → 仅删除本任务所选
    章节的净化名目录（不误伤同漫画既有章节）；
  - 3 次重试×300ms 规避 Windows 句柄占用；失败记 Log.error 并把任务消息
    置为 "Cancelled (folder cleanup failed)" 作为用户提示。

### 2. "获取图片列表"与"下载图片"并行化
- 新增独立组件 `chapter_ready_gate.dart`（有序交接门）：
  - 下载侧严格按规范序消费章节 → `_chapter/_index` 持久化语义、
    单章日志与旧实现完全一致；
  - `markReady` 先于等待也安全（就绪集合去重），`releaseAll` 保证
    pause/cancel/error 时管线不悬挂；
- `resume()` 三路径统一：
  - 新任务多章节：`_fetchImageList()` 不再被 await 阻塞整体，与
    `_runDownloadPipeline()` 并行——某章列表一到立即开始下载该章；
  - 断点恢复/单章节：`configure(allReady:true)` 退化为顺序下载；
- 原内联下载循环体逐字提取为 `_downloadChapterImages(chapterKey,order)`，
  汇总尾段提取为 `_finishTask()`，两条路径共用、零逻辑重复；
- `_scheduleTasks` 章节键改由 Gate 规范序提供（并行下 map 插入序≠完成序）；
- 并发控制不变：列表阶段受 imageListThreads+FetchConcurrencyController
  约束，图片阶段受 downloadThreads 约束，两阶段各自有界不会超订阅。

### 3. 验证
- 新增单测 `chapter_ready_gate_test.dart` **8 断言全过**——其中 G5
  （先标记后等待）抓出真实挂起缺陷并在实现中修复；
- 原 fetch_concurrency_controller 套件 58 断言保持全过；
- `flutter analyze` 三文件零问题；

## 五、安卓端"导出漫画"报错修复（16:5x）

### 现象（手机端 logs.txt 证据，经 run-as/外部存储取出）
- 16:40:31 `ZipException: Failed to write content.`——原生多线程压缩器
  （zip_flutter→kuba zip_entry_thread_write_files）线程池内失败；
- 16:40:43 重试 `ZipException: Failed to open file.`——zip_open 目标 .cbz
  返回空指针；两次均发生在 CBZ.exportVenera 的 _compress 阶段；
- 排除磁盘满：/data 252G 可用、inode 充足；
- 附带发现：失败路径泄漏暂存目录 cache/venera_export（843MB/2062 文件，
  已清理）。

### 根因
zip_flutter 的 compressFolderAsync 固定走**原生 C 多线程写入器**，在部分
安卓设备上不稳定（错误被库吞成泛化文案）；且两个导出器(CBZ/export 与
CBZ.exportVenera)的暂存目录删除不在 finally 中，压缩失败即残留数百 MB。

### 修复（lib/utils/cbz.dart，全平台生效、无源站特调）
1. `_compress` 改用同一原生库的**单线程顺序写 API**
   （ZipFile.open(level:4)+addFile/addDirectory+close），行为确定；
2. 两个导出器的暂存目录清理移入 try/finally，失败也不再泄漏；
3. 已清理设备端历史残留 843MB。

### 验证与局限
- analyze 零问题；debug APK 重建(48s 缓存命中)并覆盖安装成功、启动正常；
- 导出动作本身为 UI 流程无法 headless 复现，最终确认待用户在手机重试
  导出（预期：成功生成 .cbz 且无残留目录）。
- 安装到手机的 APK：app-debug.apk（16:5x 版）。
