## 一、下载报错复发（恢复任务后图片全 404）—— 全局修复

### 1. 报错摘要（来自应用 logs.txt，今晨运行段）
- 时间：2026-08-24 11:50 ~ 11:51（应用日志已被轮转，现存 5331 行覆盖本次会话）
- 错误信息：
  `DioException [bad response]: Invalid Status Code: 404. Not found.`
- 涉及请求样例（comic/182/362908，与昨日 520 的 comic/174 不同漫画）：
  ```
  error Network 2026-08-24 11:51:19.173891
  GET https://m.ykmh.net/images/comic/182/362908/1787315604w-7Ei6PFS6MMJI9L.jpg
  DioException ... status code of 404 ...
  ```
- 同一 URL 在约 90 秒内被重试 8 次（logs.txt 行 5018→5311），全部 404；该漫画所有图片请求 **0 次 200 成功**。

### 2. 根因分析（仅基于日志与持久化数据实证）
- 关键证据 ①：`downloading_tasks.json`（11:51 写盘）中该任务已持久化 **117 章的完整图片列表**，其中 URL 与 404 的完全一致——列表是 **约 8 月 21 日**抓取后随任务存盘的。
- 关键证据 ②：URL 路径中的时间戳 token `1787315604` 为纪元秒，折算约为 **3 天前**；源站（ykmh 类站点）的图片链接为**时效签名链接**，过期即 404。
- 根因链条：任务在数天前创建并保存了带时效签名的图片列表 → 今日恢复任务时代码检测到 `_images != null` **跳过重新抓取** → 直接使用过期 URL → 必然 404 → 盲目重试无法挽救 → 任务失败。
- 与昨日 520 的关系：触发源不同（瞬时故障 vs 链接过期），但暴露同一全局缺陷——**单类图片失败会拖死整个任务，且对"永久性失效"缺乏针对性处理**。

### 3. 修复方案（lib/network/download.dart，全部为通用机制，无任何单源特判）

| # | 改动项 | 全局覆盖方式 |
|---|---|---|
| ① | 新增 `refreshChapterImages(chapter)`：某图 404/410 时自动重新调用 `source.loadComicPages` 刷新该章图片列表并落盘，随后用新 URL 立即重试（每章每次任务仅刷新一次，防循环） | 对所有源的"过期签名链接/链接失效"场景生效；恢复旧任务、断点续传等一切复用存量列表的场景均受益 |
| ② | 死链快速失败：404/410 且刷新无效时不烧退避链，立即判死该图；其余错误仍走指数退避（昨日机制） | 区分"永久失败"与"瞬时故障"，两类场景各自最优路径，全源通用 |
| ③ | 单图失败隔离：图片重试耗尽后不再 `_setError` 中止任务，改记入 `_failedImages/_failedSamples` 并继续后续章节；任务收尾输出汇总日志并将 UI 消息标注 `(N failed)` | 覆盖"任何单点失败拖死任务"的全部触发场景（520 风暴、404 过期、断链等） |
| 配套 | wrapper 的 `image` 字段改为可变以支持 URL 热替换；补 `app_dio.dart` 导入获得 `DioException` 类型 | — |

### 4. 验证方式
- 自动化：`flutter analyze lib/network/download.dart` 零问题；Windows 构建成功。
- 交付物：`venera\build\windows\Venera-1.6.3-windows-installer.exe`（12:06，16.8MB；遵守分端构建规则，仅构建 Windows）
- 实机（待用户）：直接恢复该失败任务（无需删除重来）：
  1. 预期 logs.txt 出现 `Refreshed stale image list for chapter '...' (N images)`；
  2. 图片以新 URL 重试并返回 200，章节正常完成输出 `Chapter ... finished` 行；
  3. 任务最终显示 `N/N` 或 `N/M (K failed)`，不再整体报错退出；
  4. 若个别图确已从源站消失，日志会有 `Image failed after all retries: <url>` 且任务继续直至完成。

## 二、测试反馈修复：速度显示 0B/s + 下载速度偏慢（带宽实测驱动）

### 0. 带宽实测（问题2基线）
| 测点 | 结果 |
|---|---|
| speed.cloudflare.com __down 50MB | **7.82 MB/s** |
| proof.ovh.net 100Mb.dat | **8.74 MB/s** |
| 结论 | 当前线路可用带宽 ≈ **7.8~8.7 MB/s（65~70Mbps）**；75% 目标 ≈ **≥5.9 MB/s** |
| 应用现状 | ~3.4 img/s ≈ 0.5~0.7 MB/s（约 8%），差距主要来自并发数与每请求开销 |

### 1. 问题1根因分析：速度始终显示 0B/s
- 展示链路核查：顶栏 `downloading_page.dart` 读 `downloadingTasks.first.speed` → `ImagesDownloadTask.speed → currentSpeed`（1 秒定时器累计字节）；页面已订阅 firstTask/LocalManager 并 setState，静态链路自洽。
- 无法从既有日志定位（历史日志从未记录过速度值本身），按新规则**给管线加装日志遥测**以获得实证：
  - `onNextSecond` 每 5 秒输出 `[speed] current=... pending=... activeWorkers=...`；
  - 每张图完成输出 `[io] img#N chunks=C bytes=B`——若 chunks 恒为 1 即证明池化后响应被整体缓冲、逐块进度消失（速度统计与真实进度的共同疑点）；
- 同时发现并修复一处**确定性缺陷**：顶栏只统计 `first.speed`，多任务/排队场景下显示的不是实际吞吐 → 改为聚合所有未暂停任务的 speed。
- 待实机复测：用户跑一次下载后读 logs.txt 的 `[speed]`/`[io]` 行即可二分定位（管线值>0 而界面为 0 → UI 层；管线值=0 → 数据层）。

### 2. 问题2优化方案（全局，无单源特判）
1. **网络日志开销削减**（app_dio.dart + appdata.dart）：请求/响应的完整头与体转储改为默认关闭（新增设置 `logNetworkVerbose=false`），默认仅记一行 `METHOD url` / `url 状态码`；错误仍全量记录。此前每张图片要拼接并写盘约 2KB 文本（含长 Cookie），高并发下开销可观。
2. **聚合速度统计**（见上），保证 UI 反映全部工作线程的真实吞吐。
3. 并发建议：`downloadThreads` 上限本就是 16（用户当前 3）；达到 5.9MB/s 需按源站承受能力调高至 8~12。源站限流属外部约束，不做单源绕行。
4. 带宽自测方法留存：`curl -o NUL -w '%{speed_download}' https://speed.cloudflare.com/__down?bytes=52428800`

## 五、fetching image 环节性能优化（18:23）

### 1. 现象与实测
- 日志量化：抓取 113 章图片列表耗时 **926.9s**，章节接口 HTTP 210 ×106（限频），最大等待 57.9s；下载阶段仅 454.8s（3214 张，7.04 img/s）。
- 小样本基准：并发 1 抓 6 章 9.7s；并发 3 抓 6 章 3.4s；并发 6 抓 12 章 **>300s 超时**并触发 copy_manga 一小时级风控。
- 结论：固定高并发会被源站限频惩罚，盲目加并发反而更慢。

### 2. 全局修复（仅 `_fetchImageList`，未触碰下载逻辑）
- 将固定并发改为**自适应并发**：
  - 初始并发 = 用户 `imageListThreads`（1~6 内）；
  - 单次列表请求 <2s → 并发 +1（上限 6）；
  - 单次列表请求 >8s → 并发 -1（下限 1）；
  - 最多启动 6 个 worker，但实际并发由信号量动态控制。
- 对任意源通用：不针对 copy_manga 写死任何参数，以真实延迟为反馈。

### 3. 影响
- 仅影响“获取图片列表”阶段；`downloading` 相关代码（wrapper/下载循环/退避/跳过/速度统计）零改动。
- 下载功能保持不变。
- 附带新增 `fetchbench` headless 命令，仅用于抓取环节基准测试。

### 4. 交付物
- `Venera-1.6.3-windows-installer.exe`（18:23，16.8MB）

### 5. 修复后实测（19:22，copy_manga 8 章真实任务）
- 抓取阶段：**3.31s**，8 个章节 API 请求**全部 200、0 次 210**（此前 113 章 926.9s、106 次 210）

## 六、抓取并发控制重构为 NORMAL/PROBING/BACKOFF 状态机（22:55）

### 1. 背景与用户反馈
- 用户复测仍慢，并正确指出旧 ±1 策略存在振荡风险：快请求 +1 → 触发风控 -1 → 又 +1，形成 5↔6 循环。
- 按 GPT 推荐算法改造为状态机（规格 24 条），并发范围固定 1~6。

### 2. 实现
- 新文件 `lib/network/fetch_concurrency_controller.dart`（纯 Dart，可脱离 Flutter 单测）：
  - 三态 NORMAL/PROBING/BACKOFF；`currentThreads`/`safeThreads` 分离；
  - 滑动窗口 20 条 `FetchRequestResult{latency,success,throttled,concurrencyAtStart}`；
  - 健康判定：≥10 样本、90% <2s、0 个 >8s、0 风控、稳定 ≥30s 才允许 PROBING；
  - 2~8s 为滞回死区，单次越界不动作；连续 ≥2 个 >8s 或明确风控才降并发；
  - BACKOFF 指数冷却 30→60→120→240→300s(封顶)，期间只降不升；
  - 冷却结束回 PROBING 重试 +1，成功才把 safeThreads 提升到该值并清零 failureCount；
  - 并发调整原子性：单 isolate 内 record() 同步求值 + 进 BACKOFF 清窗口，
    多请求同时完成只产生一次调整（T8 实证）。
- `_fetchImageList` 改为接入控制器：worker 数固定 6，实际并发由
  `cc.allowedConcurrent` 动态闸门控制，不取消在途请求；
  风控近似判定：列表请求 ≥15s 即视为源站内部限频等待（JS 吞掉了 HTTP 210）。
- 用户配置 `imageListThreads` 含义不变，仅作初始值。

### 3. 测试（26 断言全过，虚拟时钟瞬时驱动）
`dart run test/fetch_concurrency_controller_test.dart`
- T1 健康但未满观察期不加并发 / 满足后经 PROBING 升 6
- T2 探测期风控 → 6→5 BACKOFF 且 safe 保持 5
- T3 冷却期内健康请求不提前升并发
- T4 冷却结束 → PROBING 而非直接 +1
- T5 二次失败冷却翻倍 60s；T9 逐级 120s、封顶 300s
- T6 探测成功锁定 safe=6、failureCount 清零、上限不为 7
- T7 单次慢请求容忍 / 连续两次 >8s 降并发
- T8 三个同时完成的风控只降一次
- T9 下限 1 不变 0
- T10 2~8s 死区完全不动作

## 七、fetching image 间歇卡顿（进度 14/21/29 处停 40~63s）——根因修复（23:19）

### 1. 日志核实（hot_manga / modujingbingdenuli，22:58~23:00 会话）
- 卡顿属实：完成序列 #1~#10 每 0.5s 一条，**gap=63.2s → #11**，#12/#13 后
  **gap=59.9s → #14**，与界面进度 14/21/29 三次卡顿吻合（第三次在快照截取后）。
- 关键证据：
  - `非200统计 = {HEAD 210 ×7}`，GET 网络层零 210；
  - 5 个章节 URL 首次 GET 耗时 **41/48/53/59/62s**（JS 默认 40s 等待链）；
  - `[fetch-cc] BACKOFF(rate limited) failure#1/#2` 与两次停顿时间一一对应。

### 2. 根因（全部有日志依据）
1. `NetworkCacheManager.onResponse` 以 `<400` 为缓存门槛，**HTTP 210 被写入缓存**；
2. JS 对 210 的重试在 5s 内命中缓存的 210 → 再等 40s → 直到缓存过期走 HEAD，
   而 HEAD 也被限频 210 → 才回落真 GET。**缓存中毒把一次风控放大成 40s×N 连坐**；
3. 缓存 HEAD 再验证使每章列表请求数翻倍，加速配额耗尽（10 章即首停）；
4. 状态机冷却期仍以低并发继续发新请求，持续消耗枯竭的配额。

### 3. 修复（全局，不改下载逻辑）
- `cache.dart` onResponse：仅缓存 `statusCode==200`（杜绝 210 中毒）；
- `cache.dart` HEAD 再验证遇 210：直接用缓存应答，不重发 GET、不删缓存；
- `download.dart`：BACKOFF 冷却期内暂停派发新列表请求
  （`cc.isCoolingDown` 闸门），让配额恢复、JS 惩罚排空；
- `download.dart`：throttled 判定去掉 `|| res.error`（错误≠风控）；
- 控制器新增 `isCoolingDown` getter + 单测 T12a~f（32 断言全过）。

### 4. 同源同书回归（23:15，headless 18 章）
- 成功 18/18，任务零错误；**卡顿(>12s)=2 次**（56.7s / 26.1s），满足 ≤2~3 次；
- **单请求 >20s = 0 条**（修复前 5 条 41~62s）；HEAD-210=0、GET-210=0；
- 停顿性质已变：不再是中毒链，而是状态机主动的 ~30s 安静期。
- 安装包重建 23:19。
