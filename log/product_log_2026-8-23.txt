## 七、追加：Windows 原生保存对话框不弹出 —— 根因修复与打包验证

### 1. 问题与根因
- 现象：Windows 端执行保存操作时，系统资源管理器的"保存"对话框始终不弹出。
- 根因：`lib/utils/io.dart` 的 `_pickNativeWindowsSavePath()` 用 `base64Encode(utf8.encode(script))` 构造 PowerShell `-EncodedCommand` 参数，但该参数**要求 Base64(UTF-16LE)**；UTF-8 字节被按 UTF-16LE 解码成乱码，PowerShell 启动即抛 `CommandNotFoundException`（exit=1），对话框从未创建。
- 实证：本机对照实验——同一脚本 UTF-8 编码 → exit=1 报错；UTF-16LE 编码 → exit=0 正常执行。
- 连带发现并一并修复：
  - 结果回写用 `Out-File -Encoding ASCII`，中文路径会变 `?`，改为 `[System.IO.File]::WriteAllText()`（UTF-8 无 BOM）；实测含繁体/全角字符路径往返无损。
  - Dart 读取侧增加 BOM 防御剥离。
  - PowerShell 参数补 `-WindowStyle Hidden`，减少控制台窗口闪现。
  - 上轮遗留的两个编译错误（单参数 `Log.info` 调用）导致无法构建，已修正为双参数。

### 2. 修改点
- 仅 `venera/lib/utils/io.dart`：新增 `_powerShellEncodedCommandBytes()`（UTF-16LE 编码）、脚本写出改 `WriteAllText`、读回剥离 BOM、进程参数加 `-WindowStyle Hidden`、修正两处 `Log.info` 调用。

### 3. 验证方式
- 自动化：UTF-16LE EncodedCommand 含中文脚本解析执行 OK；`WriteAllText` 写出中文路径文件，UTF-8 读回逐字符一致、无 BOM。
- 构建：`flutter analyze lib/utils/io.dart` 无 error（仅遗留 Share 弃用 info）；`flutter build windows --release` 成功（106.7s）。
- 实机（待用户）：安装新安装包后执行任一保存操作（如导出备份/保存封面），应弹出原生资源管理器 SaveFileDialog；选路径后文件正确落盘；若仍失败，查看应用 logs.txt 中 `SaveDialogHelper exit=...` 日志定位。

## 九、追加：全局下载速度优化（第二轮，连接层）

### 1. 慢的根因分析（全局层面）
- 现象回顾：图片下载 ~2 张/秒、UI 速率 <100KB/s，而带宽 34Mbps；第一轮已做列表并行/写盘合并后仍慢 → 单请求开销主导。
- **根因：`RHttpAdapter.fetch()` 每次调用 `rhttp.Rhttp.request()` 顶层 API，该 API 每个请求新建一个 Rust reqwest 客户端**——即每张图片都完整执行 DNS 解析 + TCP 连接 + TLS 握手，且 keepAlive 配置形同虚设（客户端随请求销毁）。按每图握手 ~0.4-0.7s 计算，与实测 2 张/秒吻合。
- 次因（已顺带修复）：`enableDnsOverrides` 判断写成 `if (!x == true)` 运算优先级错误（对纯 bool 碰巧成立、对 null 会抛异常），属隐患。

### 2. 本轮全局优化内容（不针对任何单一漫画源）
1. **Rust HTTP 客户端连接池**（`lib/network/app_dio.dart`）
   - 新增静态池 `_clientPool`，按「代理|证书校验|SNI|DNS覆盖」签名缓存 `rhttp.RhttpClient`；
   - 同签名请求复用同一持久客户端 → TCP/TLS 连接 keep-alive 生效（HTTP/2 多路复用自动启用）；
   - 创建失败自动移出池允许重试；池上限 6，超出按最旧淘汰并 dispose；
   - 受益范围：全部走 AppDio 的流量（图片下载、JS 源 API、封面缩略图等）。
2. **下载吞吐审计日志**（`lib/network/download.dart`）
   - 每章完成输出：`Chapter '<名>' finished: N images in X.Xs (Y img/s, threads=5)`；
   - 任务完成输出汇总：`Task finished: N images in X.Xs (avg Y img/s)`；
   - 写入应用 logs.txt（设置→关于→查看日志可导出），后续任何下载优化均可凭此对比生效情况。
3. DNS 开关判断修正为 `!= true`（行为不变，消除 null 隐患）。

### 3. 日志留痕机制说明
- 产品级：本文件每次会话追加优化记录（含内容与生效状态），规则见第三节。
- 应用级：上述吞吐日志自动写入 `%APPDATA%/com.github.wgh136/venera/logs.txt`（Android 为应用私有目录），无需额外配置；审计时按 "Chapter ... finished" / "Task finished" 过滤即可获取历次下载速率曲线。

### 4. 验证方法
- 自动化验证：analyze 0 issue；Windows 构建成功。
- 实机对比（待用户）：安装新安装包后重新下载同一漫画的若干章节：
  - 观察 UI 速度显示应显著高于此前 <100KB/s（预期提升数倍）；
  - 结束后在 logs.txt 中检索 `img/s`，对比本轮基线 ~1.97 张/秒；
  - 若某源仍慢，看其 img/s 与 threads 值即可判断是并发受限还是源站限流（源站限流属外部因素，不做单源硬编码规避）。
